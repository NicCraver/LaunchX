## Context

LaunchX 支持两种显示模式：简约模式（compact mode）和全屏模式（fullscreen mode）。当前问题是在简约模式下，扩展界面（如 Zed 的最近打开项目列表）的内容被错误地约束在简约模式的输入框区域内，导致内容被挤压而无法正常展开显示。

**当前状态：**
- 简约模式使用较小的窗口尺寸，主要显示搜索输入框
- 扩展界面需要更大的显示空间来展示内容列表
- 视图层级和约束系统在简约模式下未正确处理扩展界面的展开需求

**约束条件：**
- 必须保持简约模式和全屏模式的现有交互逻辑
- 不能影响全屏模式下的扩展显示
- 需要兼容所有现有扩展（Zed、VSCode 等）

## Goals / Non-Goals

**Goals:**
- 修复简约模式下扩展界面的布局问题，使其能够正确展开显示
- 确保扩展内容不被限制在输入框区域内
- 保持两种模式下扩展界面的一致性体验
- 不影响现有的模式切换逻辑

**Non-Goals:**
- 不重新设计简约模式或全屏模式的整体架构
- 不修改扩展的内部实现逻辑
- 不改变窗口尺寸的计算方式（除非必要）

## Decisions

### 1. 布局修复策略：调整视图层级和约束优先级

**决策：** 在简约模式下检测扩展界面展开时，动态调整容器视图的约束，使扩展内容视图不受输入框约束的限制。

**理由：**
- 问题根源在于约束冲突：扩展内容视图被错误地约束到输入框的边界内
- 通过调整约束优先级或移除冲突约束，可以让扩展内容正确展开
- 这种方式不需要重构整体架构，风险较低

**备选方案：**
- 方案 A：为简约模式创建独立的扩展容器视图 → 拒绝，因为会增加代码复杂度和维护成本
- 方案 B：在简约模式下临时切换到全屏模式 → 拒绝，因为会破坏用户的模式选择意图

### 2. 约束调整时机：扩展界面显示时动态调整

**决策：** 在扩展界面即将显示时（willDisplay 或类似生命周期方法）检测当前模式，如果是简约模式则调整约束。

**理由：**
- 避免在初始化时就做模式判断，保持代码简洁
- 只在需要时调整，减少不必要的性能开销
- 便于在扩展界面隐藏时恢复原有约束

### 3. 窗口尺寸处理：保持现有逻辑，仅调整内部布局

**决策：** 不修改简约模式的窗口尺寸计算，仅通过内部视图的约束调整来解决布局问题。

**理由：**
- 窗口尺寸可能涉及其他逻辑（如屏幕边界、动画等），修改风险较高
- 内部布局调整更加精准，影响范围更小
- 如果内部布局调整无法解决，再考虑窗口尺寸调整

**备选方案：**
- 方案 A：扩展展开时动态调整窗口高度 → 保留为后备方案，如果约束调整不足以解决问题

## Risks / Trade-offs

**[风险] 约束调整可能影响其他视图的布局**
→ 缓解措施：仅调整扩展容器视图的约束，不影响输入框和其他 UI 元素；充分测试各类扩展

**[风险] 模式切换时可能出现布局闪烁**
→ 缓解措施：在约束更新时使用动画过渡；确保约束更新在视图显示前完成

**[风险] 不同扩展的内容高度差异可能导致显示问题**
→ 缓解措施：使用灵活的约束（如 ≥ 而非 ==），让扩展内容自适应高度

**[权衡] 动态约束调整会增加少量性能开销**
→ 可接受：约束调整仅在扩展显示时执行一次，性能影响可忽略

## Migration Plan

**部署步骤：**
1. 修复约束逻辑并在本地测试
2. 验证简约模式和全屏模式下的扩展显示
3. 测试模式切换时的扩展行为
4. 合并代码并发布更新

**回滚策略：**
- 通过 git revert 恢复到修复前的版本
- 纯视图层改动，不涉及数据持久化，回滚无数据风险

## Open Questions

- 是否需要为不同类型的扩展（列表型、表单型等）做差异化处理？
  → 初步判断：不需要，统一的约束调整应该能覆盖所有扩展类型
- 窗口高度是否需要动态调整以适应扩展内容？
  → 待验证：先尝试纯约束调整，如果不够再考虑窗口尺寸调整
